# Design Report: Computer-Use Automation System

The through-line: **the model discovers, the artifact is the capability, deterministic replay is the production path.** Everything below is organized around keeping those three things separate and honest.

## 1. Architecture

**Shape.** One Python process, one asyncio loop, clean module boundaries, no infrastructure. `app/agent` (discovery, the only package that imports the LLM client), `app/artifacts` (schema, parameters, serialization), `app/automation` (surface abstraction, Playwright implementation, locator resolver, waits), `app/replay` (executor, checkpoints, rule engine, error taxonomy), `app/safety` (policy, redaction), `app/escalation` (session ownership, intervention manager, human-action recorder), `app/api` (operator console), `app/observability` (events, evidence). `demo_app/` is the synthetic target. `app/replay` does not import `app/agent`; the replay path has no model dependency by construction.

**Data flow.** Discovery: goal + declared inputs → `AgentLoop` observes the surface, renders a bounded, redacted observation, asks the `Planner` for one strict `Decision`, validates it against the `PolicyEngine`, resolves the chosen control with the *same* `LocatorResolver` replay uses, acts, verifies (extraction must parse; page must settle), and the `Recorder` emits a parameterized `Step` with pre/postconditions derived from what was actually observed. `finish` → `CapabilityArtifact` JSON. Replay: artifact + inputs → `validate_inputs` → `ReplayExecutor` runs each step: wait for preconditions, evaluate policy, resolve target, act, wait for postconditions, record evidence; unexpected states go through the `RuleEngine`; irreversible steps and unresolvable states go to the `EscalationManager`.

**Key decisions and trade-offs.**
- *Playwright (async) over screenshot/coordinate agents.* The target class is legacy *web*; DOM/accessibility access gives verifiable checkpoints and typed extraction that pixels cannot. Coordinates exist in the schema as a last-resort strategy (policy-gated, off by default), so a screenshot-driven surface would slot in without schema changes.
- *Local proxy application over a public site.* A hostile, table-layout, no-test-ID banking back-office with **injectable runtime conditions** (transient outage, interstitials, session expiry, duplicate controls, application error, role-based denial) is the only way to exercise the error taxonomy deterministically and without touching real systems or data.
- *Single process.* The operator must control the *same* browser page automation paused on; the console therefore runs in-process as an asyncio task next to the run, and every actor goes through one `OwnedSurface` guard. Queues/services would make the handoff harder, not easier.
- *The model picks which control; the system computes how to find it.* The LLM refers to observed controls by short refs; the recorder derives multi-strategy targets from the real DOM node and **verifies each strategy is unique on the live page before persisting it**. No model-authored selectors.
- *Application profile.* Runtime-condition rules (business outcomes, known dialogs, fatal states) are curated per vendor product (`profiles/`) and embedded into every artifact at record time. This is knowledge about the app, not about one recording, and it is the natural anchor for tenant overrides.

## 2. Artifact schema

`CapabilityArtifact` (schema_version 1.0, `extra="forbid"` throughout) is a contract, not a transcript: `name`/`version`/`description`, `target` (vendor, application, version, base_url, entry_path), `inputs`, `outputs`, `steps`, `checkpoint`, `conditions` (runtime rules), `policy` (what the capability needs to be allowed to do), `compatibility` (vendor/product/supported versions/tenant profile), `metadata` (goal, run id, model, decision count).

- **Typed inputs**: type, required, `sensitive`, pattern, enum. Sensitive inputs are never stored, never logged, and must be supplied from a secret source. Numeric inputs get a conservative inferred pattern (`^\d+$`).
- **Typed outputs with provenance**: every output declares its `source` — `status` (success or a business-outcome status enumerated from the profile), `extract` (which step produced it, nullable when a business outcome pre-empts it), `input` (echo), `rule_message` (the application's own message). Model validators reject outputs that no step produces.
- **Steps**: `id`, `action` (navigate/click/type/select/press/extract), `target`, `arguments` (values as `${input}` placeholders), `preconditions`, `postconditions`, `timeout_s`, `retry_policy` (1 attempt for irreversible steps), `risk_class`, `on_error` (fail/escalate), `evidence_policy`.
- **TargetSpec**: one control described by up to eight strategies tried in a **fixed priority**: accessibility role+name → associated label → stable semantic attributes (tag/name/type/value/title/href) → exact visible text → semantic `table_cell` (row text + column header, table header signature) → CSS → XPath → coordinates (with the viewport they assume). `within` scopes semantic strategies to a container (form, nav strip, classed table) — how a human disambiguates "the Search button in the lookup form". `fallbacks` hold alternative controls (a tenant whose button reads "Find"). `frame` is reserved and explicitly rejected by the v1 resolver rather than silently ignored. Every strategy in a recorded artifact was unique on the page at record time.
- **Conditions** (discriminated union): `url_matches` (regex over the path, parameter values regex-escaped at check time), `text_present/absent`, `heading_present` (page title, immune to nav text), `element_visible/hidden/enabled`, `element_value` (verifies type/select), `all_of/any_of/not`. Checkpoints are derived from the observed before/after page states; an LLM-supplied `expected_heading` is kept only if it was actually observed.
- **Why the transcript is not the capability**: a transcript is a record of one model's reasoning against one concrete page; it cannot be validated, diffed, parameterized, or reviewed for risk. The artifact can be. The transcript is kept as *evidence* (`llm-call-NN.json`, redacted) so a reviewer can see discovery happened.

## 3. Determinism & error handling

**No model in the loop.** `ReplayExecutor` has no planner and no import path to one; `ReplayResult.llm_calls` is asserted to be 0 by tests and the event log contains no `LLM_*` events. Same artifact + same inputs → same actions.

**Locator resolution.** Strategies run in priority order; a strategy matching several usable elements is never used. Two policies matter: a more specific *semantic* strategy may break a tie; a *structural* one (CSS/XPath) may only recover from **drift** (semantic strategies matched nothing — flagged as `drift_fallback` for artifact maintenance) and never break a semantic tie, because a positional selector cannot know which of two identical "Search" buttons is right → `AMBIGUOUS_TARGET`. Ambiguity is confirmed on two consecutive polls, then fails fast. Every attempt is recorded (`locator_diagnostics`) so the failure explains itself.

**Waits.** No sleeps as synchronization. Each step waits for its postconditions with bounded polling (`wait_for_expected_state`), and the rule engine is evaluated on each poll so a business outcome or known dialog is recognized in ~0.5 s instead of after the timeout. A rule must match on two consecutive polls, so a stale page caught mid-navigation cannot trigger a spurious outcome. Slow pages simply take longer (tested with 1.2 s injected latency).

**Taxonomy.** `ReplayResult.status ∈ {SUCCESS, BUSINESS_OUTCOME, RECOVERABLE_EXHAUSTED, HARD_FAILURE, ESCALATED}` with a `Failure{category, code, message, expected, observed, step_id, screenshot_ref, details}`.
- *Business outcomes* (`MEMBER_NOT_FOUND`, `INSUFFICIENT_PERMISSION`, `VALIDATION_REJECTED`) are legitimate answers: `status` output set from the rule (e.g. `not_found`), the application's own message captured, extracted outputs `null`.
- *Recoverable* (`TRANSIENT_LOAD` → retry the step, `KNOWN_DIALOG`/`SESSION_REFRESH_REQUIRED` → click the dismiss control) are applied under a per-rule budget; exhaustion is its own status.
- *Hard failures* are system-defined (`INVALID_INPUT` before any browser action, `ARTIFACT_INCOMPATIBLE`, `TARGET_NOT_FOUND`, `AMBIGUOUS_TARGET`, `PRECONDITION_FAILED`, `CHECKPOINT_FAILED`, `POLICY_VIOLATION`, `ACTION_FAILED`, `EXTRACTION_FAILED`, `REPLAY_TIMEOUT`) or profile-defined (`SESSION_LOST`, `AUTHENTICATION_FAILED`, `UNEXPECTED_STATE` for the application-error page).
Rules are consulted only when an expected state is not reached, so a "must be" on some unrelated page can never mis-classify a successful step. **Evidence**: every failure writes a screenshot (password fields masked) and the redacted page text; every run writes `events.jsonl`, `result.json`, a final screenshot, and intervention records.

**Drift (secondary).** Semantic-first targets survive restyling and reordering; `drift_signals` in the result flag steps that needed a structural fallback, which is the trigger to re-record or add a tenant override.

## 4. Heterogeneity & multi-tenant

**Surface seam.** `ComputerSurface` (observe, navigate, click, click_at, type, select, press, read_text, screenshot, current_url, page_text, page_headings, wait_for_settled) plus `StrategyBackend.match(spec, strategy, scope)` is the entire perception/action interface. The artifact references only `TargetSpec` strategies and `Condition`s. `PlaywrightSurface` implements both today. A **legacy web** app with framesets would extend the backend with `frame` handling (the field already exists and is rejected explicitly, not ignored); accessibility-tree-only pages already work because role/name is the first strategy. A **desktop** surface (`AccessibilitySurface` over UIA/AT-SPI, or a screenshot+coordinates surface) implements the same protocol: role/name and label map onto accessibility properties, `table_cell` onto grid patterns, CSS/XPath strategies are absent, coordinates become more prominent. Nothing in `app/replay` or the schema changes.

**Multi-tenant reuse.** The artifact separates *what the flow does* (steps, semantic targets, conditions) from *where it runs* (`target.base_url`, overridable at replay — the compose file uses this to run the same artifact against a different host) and from *what the app can do at runtime* (the embedded profile rules, curated per vendor product). The intended model is `base artifact (vendor product) → tenant/version override → replay`: an override is a small document keyed by artifact name + tenant that may replace a step's target (`fallbacks` are the in-artifact form of this), add tenant-specific rules (a bank-branded interstitial), and change `base_url`, roles and input patterns. `compatibility.supported_versions` and `tenant_profile` record what an artifact was validated against. **Drift detection** comes from replay itself: `drift_signals`, `strategies_used` and `TARGET_UNRESOLVED` events per tenant are the signal that a tenant needs an override or a re-record; unattended replays fail safely (`ESCALATED`, nothing guessed) until someone approves the fix.

## 5. Escalation & handoff

**Stuck detection.** Discovery: the model asks (`escalate`), the same proposal repeats on an unchanged screen N times, or policy demands confirmation. Replay: an unresolvable/ambiguous target, an unrecognized state (checkpoint failed, no rule matched) on a step with `on_error: escalate`, or an irreversible step needing approval. Operators can also request a pause at the next step boundary.

**Intervention request.** `InterventionRequest{id, run_id, capability, goal, kind, reason, current_step, pending_action, screenshot, url, page_excerpt, details (expected/observed/locator diagnostics), status, human_action_log}` is persisted to evidence and served by the console.

**Same-session takeover.** The console runs inside the run's process on a second port and acts on the *same Playwright page*. Ownership is a state machine enforced in code: `AUTOMATION → ESCALATED (nobody acts) → HUMAN_CONTROL → RESUMING → AUTOMATION`, or `ESCALATED → AUTOMATION` on approval, or `→ ABORTED`. `OwnedSurface` wraps the one real surface per actor and refuses mutations unless that actor owns control; read-only operations stay available so the console can show the live screen while paused. Console actions are proxied through the same resolver/executor primitives and recorded exactly; with `HEADLESS=false` the human may also click directly in the window, and an injected capture-phase DOM listener records those clicks (password values masked), gated on `HUMAN_CONTROL` so automation's own synthetic events are never attributed to a person.

**Resume.** After release the executor re-verifies rather than assumes: if the step's postconditions hold the human completed it; if the screen has not moved on it retries the step once; if it has, it resumes at the first later step whose entry state (preconditions) matches and records the skipped steps as `human_completed_steps`. Anything else ends as `ESCALATED/UNRESOLVED_AFTER_HANDOFF`, never a guess. Approval makes automation perform the gated action itself; abort/timeout/no-operator end the run as `ESCALATED` with a specific code.

**Intentionally minimal.** The console is server-rendered HTML with a 2-second screenshot refresh and a JSON API, not a co-browsing stream; it is bound to one run and one process; there is no operator identity/audit beyond notes. The mechanism (pause, expose the live session, act, record, release, verified resume) is real and tested end to end.

## 6. Safety

- **Allowlist**: URL regex allow- and deny-lists (the fault-injection console is denied even though it is on the same host); navigation targets and the current page are both checked; action allowlist per policy. Enforced before every action in both discovery and replay, independent of the model.
- **Risk classes**: declarative rules classify by action, control name pattern, input type and route: SAFE (navigation, search, reading) executes; SENSITIVE (credentials, data entry on account screens) executes only if the policy permits it; IRREVERSIBLE (commit controls, anything but Back/Cancel on a review screen) requires a human approval and can never be retried automatically. The model or artifact may *raise* a classification, never lower it.
- **Secrets**: sensitive inputs are supplied via `env:VAR`, the model only ever sees `${access_code}`, the value is substituted at the surface, a policy rule forbids typing a secret into an unmasked field, and screenshots mask password inputs. The LLM API key is registered with the process redactor.
- **Redaction**: a single `Redactor` scrubs known secret values, secret-like keys and PII patterns (account/card numbers, SSNs, emails, phones) from events, evidence text, intervention records and the observation *before it leaves the process*.
- **Limits**: unfamiliar states escalate instead of being handled creatively; the demo's regulated-data story is only as good as the pattern list (names cannot be pattern-detected — production evidence needs access control and retention); screenshots inherently contain page content; the console has no authentication because it binds to localhost for one run; policy cannot reason about the *meaning* of a form it has never seen — that is what SENSITIVE-by-route and human confirmation are for.

## 7. Cuts

Not built, deliberately: **frames/framesets** (schema seam present, resolver rejects explicitly); **desktop/accessibility surface** (protocol designed for it, no implementation); **tenant override files and a version detector** (the model is described and the hooks — `base_url`, `fallbacks`, `compatibility` — exist, but no override loader); **assisted LLM recovery on replay** (a single-step, policy-checked, evidence-recorded fallback would be a stretch, and it must never become a hidden model dependency of the production path); **artifact approval workflow and stability scoring** (draft→approved gating, N-run flakiness); **a persistent capability catalog/API** for agents (artifacts are files; the CLI is the interface); **operator authentication, streaming co-browsing, multi-run console**. Next, in order: tenant overrides + drift dashboard from `drift_signals`, approval state on artifacts, frames, then the assisted-recovery stretch. All of these were lower priority than a replay engine that verifies every transition, classifies every failure, refuses to guess, and can hand the live session to a person and take it back.
